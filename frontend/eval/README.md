# Измерение free-совета

Этот каталог гоняет настоящий браузерный движок (`src/engine/browser/council.js`) на задачах с точным ответом и сравнивает полный совет с более простыми вариантами. Он не меняет Stage 2 и интерфейс. Числа из отчёта сами по себе не являются решением о продукте.

Ключ, который раньше лежал в исходниках, из рабочего дерева убран. Отзыв ключа владельцем и пересборка Pages не подтверждены. Общий ключ не используется. CLI берёт только `OPENROUTER_API_KEY` из окружения или из `.env` в корне репозитория и отказывается от ключа с известным опубликованным хешем. Значение ключа не печатается.

Тексты GPQA и варианты ответов остаются в `frontend/eval/.cache/` и не попадают в отчёт, цитаты и журнал прогресса. Каталог `.cache` и `.runs` не коммитятся.

## Команды

Из корня репозитория:

```text
npm --prefix frontend run eval -- prepare
npm --prefix frontend run eval -- preflight
npm --prefix frontend run eval -- smoke
npm --prefix frontend run eval -- dev
npm --prefix frontend run eval -- test
npm --prefix frontend run eval -- report
```

`--run <id>` выбирает каталог `frontend/eval/.runs/<id>`. По умолчанию это `main`. Повтор той же команды продолжает тот же журнал. Второй процесс с тем же каталогом не стартует.

Коды выхода: 0 — шаг завершён, 2 — пауза по квоте или незавершённый отчёт, 1 — ошибка протокола или остановка из-за смены состава моделей.

`prepare` скачивает источники. Если GPQA закрыт, положите JSONL в `frontend/eval/.cache/manual/` (`aime2025.jsonl`, `aime2026.jsonl`, `gpqa.jsonl`, `mmlu-validation.jsonl`, `mmlu-test.jsonl`) и не коммитьте их.

`smoke` — две отдельные задачи и временный состав по размеру модели. Это проверка обвязки, не результат точности.

`dev` выбирает модель B, совет и председателя H и только после этого пишет `manifest.json` с `frozen: true`. `test` не делает ни одного вызова, пока этот файл и хеш протокола не совпадут. После 40 тестовых вопросов выполняется только операционная проверка. N и семья сравнений не меняются.

`report` пишет `report.md` (русский, полный), `report.json` и `summary.md` (английские таблицы) в каталог прогона и обновляет раздел между `<!-- eval-results:start -->` и `<!-- eval-results:end -->` в корневом `README.md`. Команду можно запускать в любой момент, в том числе пока `test` ещё идёт: она читает только сохранённые файлы вопросов и не берёт блокировку. Если завершённых test-вопросов меньше 120, отчёт помечен как промежуточный, заголовочный вывод не делается, код выхода 2. Когда все вопросы завершены, та же команда даёт окончательный отчёт и код 0. `--no-readme` оставляет README без изменений.

`repair` повторно выполняет только слоты, которые в основном прогоне не дали ответа (сеть, таймаут, upstream 429, ошибка провайдера, обрезанный поток). Успешные free-ответы переиспользуются без нового запроса. Где в каталоге есть платный id, вызов идёт на него ключом `or_key`; иначе повторяется тот же `:free` id. Результат пишется в `frontend/eval/.runs/<id>/repair/` и не меняет as-run. Повтор той же команды продолжает с места остановки. `--max-usd` по умолчанию 15, `--max-posts` по умолчанию 1500, `--jobs` по умолчанию 4: столько вопросов идут сразу, а free-вызовы остаются в одной последовательной очереди. Код 2 — пауза по лимиту, сети или потому что основной test ещё не дошёл до конца.

`a8` — отдельная кампания «платный консилиум против Self-MoA» в `frontend/eval/.runs/a8-open-v1/`. Она не пишет в `main`, `a8-strong-v1`, repair, complete и не обновляет раздел результатов README. Фаза обязательна. Модельные POST только с `--live`. Бюджет $60 и 4000 POST общий для probe, dev, smoke, pilot и test; повтор команды не поднимает лимит. Primary-пара — A8 против S8. Отчёт оффлайн: `--phase report`.

```text
npm --prefix frontend run eval -- a8 --phase preflight --run a8-open-v1 --live
npm --prefix frontend run eval -- a8 --phase probe --run a8-open-v1 --live
npm --prefix frontend run eval -- a8 --phase dev --run a8-open-v1 --live
npm --prefix frontend run eval -- a8 --phase smoke --run a8-open-v1 --live
npm --prefix frontend run eval -- a8 --phase pilot --run a8-open-v1 --live
npm --prefix frontend run eval -- a8 --phase test --run a8-open-v1 --live
npm --prefix frontend run eval -- a8 --phase report --run a8-open-v1
```

`a8-open-v3` продолжает v1 и v2, а не начинает заново. `--from` задаётся один раз на preflight и закрепляется в `campaign.json`; preflight берёт снимок маршрутов первого источника без сети, потому что новый endpoint меняет `provider` и hash каждого запроса. Слот из источника переиспользуется только под точным ключом с hash полного запроса (модель, маршрут, промпт, caps, decoding). Ответ берётся как есть, в том числе неверный. Слот, исчерпавший обе попытки, переносится как отказ. Остальные слоты вызываются снова, и уже потраченные на них попытки входят в тот же лимит 2. Probe всегда идёт live: он проверяет, что маршруты отвечают сегодня. Расход и POST источников входят в тот же потолок $60 / 4000 и показываются в отчёте отдельно.

Stage 2 и председатель видят ответы в порядке завершения вызовов; переиспользованные идут первыми в порядке источника. Поэтому промпты Stage 2 и синтеза v1 воспроизводятся байт в байт. Правила рук записаны в `campaign.json`: A8 требует все три ответа Stage 1, S8 — все пять генераций с текстом, иначе рука считается отказом метода. В v1 S8 сводил любые непустые генерации, поэтому v1 и v3 — не один протокол.

Внутри вопроса Stage 1 и четыре генерации B идут параллельно, затем параллельно ветки A8 (Stage 2 → синтез) и S8. `--jobs` (по умолчанию 6) вопросов идут сразу, `--in-flight` ограничивает HTTP всего прогона (по умолчанию jobs × 7), `--model-in-flight` — одной модели (по умолчанию 6). Вопрос в cooldown остаётся pending, остальные продолжают. Пауза сети или in-flight бюджета ключа не завершает процесс: он ждёт и делает следующий проход, до `--max-resumes` (по умолчанию 30). Нехватка кредита, ключ, потолок трат и fatal завершают фазу кодом 2 или 1.

```text
npm --prefix frontend run eval -- a8 --phase preflight --run a8-open-v3 --from a8-open-v1,a8-open-v2
npm --prefix frontend run eval -- a8 --phase probe --run a8-open-v3 --live
npm --prefix frontend run eval -- a8 --phase dev --run a8-open-v3 --live
npm --prefix frontend run eval -- a8 --phase smoke --run a8-open-v3 --live
npm --prefix frontend run eval -- a8 --phase pilot --run a8-open-v3 --live
npm --prefix frontend run eval -- a8 --phase test --run a8-open-v3 --live
npm --prefix frontend run eval -- a8 --phase report --run a8-open-v3
```

`a8-open-v4` проверяет, что именно потерял конвейер в v3. Там 155 из 360 ответов судей упёрлись в лимит 4096 токенов, 81 не дошёл до строки `FINAL RANKING`, а синтез A8 обрезался на 8192 токенах в 22 вопросах против 13 у S8; все обрезанные ответы получили ноль. В v4 лимиты Stage 2 и обоих синтезов задаются на preflight флагами `--stage2-cap` и `--final-cap` и закрепляются в `campaign.json`; лимит Stage 1 и генераций B не меняется, поэтому эти слоты берутся из v1–v3 по hash запроса, а Stage 2 и синтезы вызываются заново. Дедлайн потока растёт вместе с самым большим лимитом (`streamTimeoutSeconds`, из расчёта 8 токенов в секунду плюс 120 с на заголовки), иначе движок обрывал бы длинный ответ по своим 600 с. Дедлайн не входит в тело запроса и в hash. Preflight отказывает, если какой-то маршрут не может выдать новый лимит. Источник с другими лимитами допускается: разница записывается в `campaign.json` (`sourceDifferences`), а защита от чужого слота остаётся за hash.

Новая рука P8 — большинство по трём ответам Stage 1 совета, без дополнительных вызовов; ответ без разбираемой последней строки воздерживается, ничья решается seeded hash, как A4 в `main`. Правило неполного состава у P8 то же, что у A8. Primary-пара прежняя: A8 против S8. Пары P8 против S8 и P8 против A8 вторичные, с одной поправкой Холма на семью; они не заменяют основной вывод. В v3 такое большинство дало бы 103 из 120, столько же, сколько S8.

```text
npm --prefix frontend run eval -- a8 --phase preflight --run a8-open-v4 --from a8-open-v1,a8-open-v2,a8-open-v3 --stage2-cap 16384 --final-cap 16384
npm --prefix frontend run eval -- a8 --phase probe --run a8-open-v4 --live
npm --prefix frontend run eval -- a8 --phase dev --run a8-open-v4 --live
npm --prefix frontend run eval -- a8 --phase smoke --run a8-open-v4 --live
npm --prefix frontend run eval -- a8 --phase pilot --run a8-open-v4 --live
npm --prefix frontend run eval -- a8 --phase test --run a8-open-v4 --live
npm --prefix frontend run eval -- a8 --phase report --run a8-open-v4
```

### a8-open-v5: общий максимальный лимит, новые блоки, защита от цикла

v5 — отдельная кампания со своим бюджетом. Она берёт у v4 только снимок маршрутов (`--routes-from a8-open-v4`): ни один слот не переиспользуется, расход v1–v4 не переносится. Потолок задаётся на preflight (`--max-usd 100 --max-posts 6000`) и потом не меняется.

**Заморозка метода.** Хеш исходников покрывает все локальные модули, которые загружает `a8.js`, прямо или через другие модули; тест следит, чтобы список совпадал с реальным замыканием импортов. Preflight v5 отказывает, если какой-то из этих файлов изменён или не закоммичен, и записывает коммит в `campaign.json` (`gitHead`). Поэтому код коммитится до preflight, а все фазы, кроме report и loops, сверяют хеш.

**Лимиты.** `--caps max` ставит один лимит на все стадии: самый большой, который выдерживает каждый маршрут шортлиста. Это `min(maxCompletion, (context − 8000) / 6)`, сегодня 32768 (StepFun). Лимит генераций B всегда равен лимиту Stage 1: первый ответ B — это sample 1. Preflight отказывает, если синтезу S8 (`6 × лимит + 8000`) или судье (`5.5 × лимит + 8000`) не хватает контекста какого-то маршрута; перед каждой отправкой собранный промпт сверяется с контекстом ещё раз (2 символа на токен плюс запас), и при превышении вызов отказывает с причиной `context`, текст не урезается. Дедлайн потока растёт до 4216 с. Probe подтверждает лимит, только если запрос с ним вернул завершённый поток с `usage`; в v5 probe не заменяет маршрут сам, а останавливается. Пока лимит не подтверждён на всех маршрутах, probe не считается законченным и dev не стартует. Повторный запуск probe опрашивает только неподтверждённые маршруты, новой попыткой того же запроса. Если маршрут отвечает 400 или 404, лимит этой кампании ему не подходит; лимиты фиксируются на preflight, поэтому нужна новая кампания с явными флагами лимитов.

**Защита от цикла.** Опция движка `loopGuard` (по умолчанию выключена; продукт её не включает) сравнивает последние 4000 символов рассуждения с 24000 символами перед ними по шинглам длиной 40. Проверки идут через каждые 2000 символов накопленного текста, поэтому решение не зависит от того, как сеть порезала поток; срабатывание — 80% совпадений на двух проверках подряд. Детектор читает один канал рассуждения (провайдеры дублируют его в `reasoning` и `reasoning_details`) и отдельно видимый текст. Первая зациклившаяся попытка отменяется и повторяется один раз, в пределах двух HTTP-попыток на слот вместе с повторами 429; если зациклилась и последняя, её накопленный текст сохраняется с пометкой `loopCut` и оценивается как написан. Прогон по сохранённым SSE v3 и v4 через тот же парсер: судьи v4 — 20 из 51 обрезанных и 4 из 309 дописанных (настоящие циклы, которые сами закончились через 7–16 тыс. токенов), судьи v3 — 5 из 107, синтезы — 2 из 39, Stage 1 — 1 из 42, генерации B — 0; на дописанных Stage 1, генерациях и синтезах — 0.

**Хвостовое правило.** Ответ, оборванный лимитом или детектором до видимого текста, передаётся судьям, председателю и в синтез S8 как пометка и последние 8000 символов его рассуждения. Так же обрабатывается обрезанный текст судьи до разбора замечаний и спорных утверждений. Дописанные ответы идут целиком. Все оценки читают исходный сохранённый текст. Это отличает v5 от продукта и от v4.

**Блоки.** `a8 --phase prepare` строит `.cache/bank-a8x.json` рядом с базовым банком, который не меняется. Строки Hugging Face скачиваются один раз и замораживаются в `.cache/raw` с записанным sha репозитория.

| Блок | Источник | Test | Dev |
|---|---|---|---|
| `rgym` | reasoning-gym 0.1.25, шесть семейств с целым ответом, генерация `tools/rgym_generate.py` | 60 | 4 |
| `amc` | AMC 10A и 12A 2026, ручной перенос по `tools/amc_ingest.js`, ключ Think Academy (неофициальный) | 37 | — |
| `arxiv` | MathArena ArXivMath 08 и 09.2026, числовое подмножество | 46 | 4 |
| `hmmt` | MathArena HMMT February 2026, числовое подмножество | 20 | 4 |
| `livemath` | LiveMathBench 202505 (зеркало), задачи с целым ответом | 39 | 4 |

Числовое подмножество — задачи, чей эталон читается как одно целое или несократимая дробь; правило смотрит только на эталон. Это не весь исходный бенчмарк: отчёт показывает охват каждого источника и причины исключений. Новый вид ответа `number` канонизирует целые любого размера и дроби через BigInt; инструкции для `integer` и `choice` не менялись. В reasoning-gym до первого вызова модели исключено семейство `simple_geometry` (противоречивые «выпуклые» многоугольники), а `number_sequence` получает не меньше шести членов. Эталоны AMC проверены вручную или перебором; задачи, которым нужен рисунок, не взяты. В пяти задачах AMC (12A #2, #10, #14, #16, #22) рисунок убран или переписан текстом; они помечены `adapted`, и отчёт показывает основной результат ещё и без них. HMMT February 2026 #32 исключена по списку `MANUAL_EXCLUSIONS` до первого вызова: она просит все возможные значения и велит записать список в `\boxed`, что спорит со строкой `ANSWER` с одним числом. Инструкция вида `number` сообщает модели, что ответ одно рациональное число. В семи задачах ArXivMath условие допускает ответ +∞, и инструкция этот вариант исключает. Подсказка одинакова для всех рук, но абсолютная точность поэтому не сравнима с таблицами MathArena. `report --gold-overrides <file>` пересчитывает все руки по исправленным эталонам без новых вызовов и пишет `report-corrected.md` рядом с исходным.

**Что сравнивается.** Основная пара — A8 против S8 на пяти новых блоках. Вторичная семья под одной поправкой Холма: A8 − S8 в группе A, A8 − S8 в группах B и C вместе, A8 − S8 на прежних 120 вопросах, A8 − P8 и S8 − P8. Группа считается по самой ранней известной дате материала против дат листинга выбранных моделей: A — после всех или сгенерировано, B — после части, C — до всех. Состав групп известен только после dev, потому что зависит от выбранного совета; H всегда входит в совет. При совете v4 группа B — один месяц ArXivMath, слишком мало для отдельной проверки, поэтому в семье она объединена с C, а A, B и C по отдельности идут в диагностику. В группу A попали только reasoning-gym и AMC, так что разница между группами смешивает свежесть с типом задач. Дата листинга — не дата отсечения знаний, поэтому ни одна группа не объявляется свободной от утечки. p ≥ 0.05 не читается как равенство методов.

Test идёт сначала по всем новым блокам, потом по прежним: пауза по бюджету оставит неполной вторичную пару, а не основную. Кампании v1–v4 сохраняют прежний порядок. Мягкое чтение ответа (`LENIENT_RULES`) — только диагностика: отчёт перечитывает сохранённые финальные тексты A8, S8 и B8 и показывает их точность и пару A8 − S8 рядом со строгими. P8 мягко не перечитывается, потому что его бюллетени хранят только строгие ответы.

**Pilot и шлюз.** Pilot берёт по два dev-вопроса на блок в заранее заданном порядке и считает прогноз test по блокам: средний и консервативный, с удержанными резервами по полной цене. Консервативный прогноз — 90-й процентиль, а при двух–четырёх вопросах на блок это просто самый дорогой из них. В прогноз идут только вызовы сравнения: свои вызовы dev делала на тех же вопросах, и они не считаются. Если консервативный прогноз не помещается в остаток, pilot сам расширяется до четырёх вопросов на блок. Test не стартует, пока шлюз не пройден, если не передан `--accept-forecast`.

**Проверка циклов перед test.** `a8 --phase loops --of pilot` восстанавливает каждую остановку детектора по сохранённому телу потока: модель, стадию, позицию, долю повтора, итог слота и текст перед остановкой. Список пишется в `reports/loops-pilot.json`. Каждую остановку человек читает до test; остановка на тексте, который не зацикливался, останавливает кампанию. Фаза ничего не отправляет и может идти рядом с работающей фазой.

**Расход.** Прерванный поток не приносит `usage`, и его резерв остаётся удержанным. Каждая попытка сохраняет `generationId`; `a8 --phase reconcile` спрашивает OpenRouter фактическую стоимость через `/api/v1/generation` и заменяет резерв ею, один раз. Неизвестная стоимость не становится нулём. В начале каждой фазы reconcile идёт сам, а счётчик ключа пишется как аудит, без влияния на резервы. `--self-test` один раз намеренно обрывает короткий вызов на маршруте B и проверяет, что его цена находится; это платный вызов, поэтому он требует `--live`.

Известное ограничение. Модели отвечают в видимом тексте почти только строкой `ANSWER`, всё решение остаётся в скрытом рассуждении. Поэтому судьи и председатель A8 видят у дописанных ответов голые ответы без решения.

```text
npm --prefix frontend run eval -- a8 --phase prepare
npm --prefix frontend run eval -- a8 --phase preflight --run a8-open-v5 --routes-from a8-open-v4 --caps max --blocks rgym,amc,arxiv,hmmt,livemath --max-usd 100 --max-posts 6000
npm --prefix frontend run eval -- a8 --phase probe --run a8-open-v5 --live
npm --prefix frontend run eval -- a8 --phase dev --run a8-open-v5 --live
npm --prefix frontend run eval -- a8 --phase smoke --run a8-open-v5 --live
npm --prefix frontend run eval -- a8 --phase loops --run a8-open-v5 --of smoke
npm --prefix frontend run eval -- a8 --phase reconcile --run a8-open-v5 --self-test --live
npm --prefix frontend run eval -- a8 --phase pilot --run a8-open-v5 --live
npm --prefix frontend run eval -- a8 --phase loops --run a8-open-v5 --of pilot
npm --prefix frontend run eval -- a8 --phase test --run a8-open-v5 --live --jobs 12 --model-in-flight 12
npm --prefix frontend run eval -- a8 --phase reconcile --run a8-open-v5
npm --prefix frontend run eval -- a8 --phase report --run a8-open-v5
```

`complete` запускается после repair на все 120 вопросов. Однозначный ответ, записанный не в строгом формате (жирный `ANSWER`, скобки, `\boxed{}`, строка `ANSWER` не последняя, последняя строка «the answer is X»), читается из уже полученного текста и не запрашивается снова. Ячейка, в которой ответа нет, рисуется заново тем же запросом и тем же endpoint, до `--attempts` раз (по умолчанию 3). Stage 2, red team и Stage 3 повторяются из журнала repair без новых вызовов: новый розыгрыш Stage 1 меняет только оценку ячеек, которые его читают. Результат пишется в `frontend/eval/.runs/<id>/complete/` и не меняет as-run и repair. `--max-usd` по умолчанию 20, `--max-posts` по умолчанию 600, `--jobs` по умолчанию 4. `--cooldown-seconds` ограничивает паузу после upstream 429 (без флага остаётся обычные 10 минут). `--deadline-minutes` держит процесс живым и повторяет охлаждённые ячейки до абсолютного срока, записанного в state; после срока ячейка, которую провайдер всё ещё не отдаёт, считается неверной с пометкой provider unavailable, а голос A4 собирается из остальных ответов. Код 2 — пауза по лимиту или сети.
