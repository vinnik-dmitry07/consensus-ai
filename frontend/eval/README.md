# Измерение free-совета

Этот каталог гоняет настоящий браузерный движок (`src/engine/browser/council.js`) на задачах с точным ответом и сравнивает полный совет с более простыми вариантами. Он не меняет Stage 2 и интерфейс. Числа из отчёта сами по себе не являются решением о продукте.

Ключ, который раньше лежал в исходниках, из рабочего дерева убран. Отзыв ключа владельцем и пересборка Pages не подтверждены. Общий ключ не используется. CLI берёт только `OPENROUTER_API_KEY` из окружения или из `.env` в корне репозитория и отказывается от ключа с известным опубликованным хешем. Значение ключа не печатается.

Тексты GPQA и варианты ответов остаются в `frontend/eval/.cache/` и не попадают в отчёт, цитаты и журнал прогресса. Каталог `.cache` и `.runs` не коммитятся.

## Команды

Из корня репозитория:

```text
npm --prefix frontend run eval -- prepare
npm --prefix frontend run eval -- preflight
npm --prefix frontend run eval -- smoke
npm --prefix frontend run eval -- dev
npm --prefix frontend run eval -- test
npm --prefix frontend run eval -- report
```

`--run <id>` выбирает каталог `frontend/eval/.runs/<id>`. По умолчанию это `main`. Повтор той же команды продолжает тот же журнал. Второй процесс с тем же каталогом не стартует.

Коды выхода: 0 — шаг завершён, 2 — пауза по квоте или незавершённый отчёт, 1 — ошибка протокола или остановка из-за смены состава моделей.

`prepare` скачивает источники. Если GPQA закрыт, положите JSONL в `frontend/eval/.cache/manual/` (`aime2025.jsonl`, `aime2026.jsonl`, `gpqa.jsonl`, `mmlu-validation.jsonl`, `mmlu-test.jsonl`) и не коммитьте их.

`smoke` — две отдельные задачи и временный состав по размеру модели. Это проверка обвязки, не результат точности.

`dev` выбирает модель B, совет и председателя H и только после этого пишет `manifest.json` с `frozen: true`. `test` не делает ни одного вызова, пока этот файл и хеш протокола не совпадут. После 40 тестовых вопросов выполняется только операционная проверка. N и семья сравнений не меняются.

`report` пишет `report.md` (русский, полный), `report.json` и `summary.md` (английские таблицы) в каталог прогона и обновляет раздел между `<!-- eval-results:start -->` и `<!-- eval-results:end -->` в корневом `README.md`. Команду можно запускать в любой момент, в том числе пока `test` ещё идёт: она читает только сохранённые файлы вопросов и не берёт блокировку. Если завершённых test-вопросов меньше 120, отчёт помечен как промежуточный, заголовочный вывод не делается, код выхода 2. Когда все вопросы завершены, та же команда даёт окончательный отчёт и код 0. `--no-readme` оставляет README без изменений.

`repair` повторно выполняет только слоты, которые в основном прогоне не дали ответа (сеть, таймаут, upstream 429, ошибка провайдера, обрезанный поток). Успешные free-ответы переиспользуются без нового запроса. Где в каталоге есть платный id, вызов идёт на него ключом `or_key`; иначе повторяется тот же `:free` id. Результат пишется в `frontend/eval/.runs/<id>/repair/` и не меняет as-run. Повтор той же команды продолжает с места остановки. `--max-usd` по умолчанию 15, `--max-posts` по умолчанию 1500, `--jobs` по умолчанию 4: столько вопросов идут сразу, а free-вызовы остаются в одной последовательной очереди. Код 2 — пауза по лимиту, сети или потому что основной test ещё не дошёл до конца.

`a8` — отдельная кампания «платный консилиум против Self-MoA» в `frontend/eval/.runs/a8-open-v1/`. Она не пишет в `main`, `a8-strong-v1`, repair, complete и не обновляет раздел результатов README. Фаза обязательна. Модельные POST только с `--live`. Бюджет $60 и 4000 POST общий для probe, dev, smoke, pilot и test; повтор команды не поднимает лимит. Primary-пара — A8 против S8. Отчёт оффлайн: `--phase report`.

```text
npm --prefix frontend run eval -- a8 --phase preflight --run a8-open-v1 --live
npm --prefix frontend run eval -- a8 --phase probe --run a8-open-v1 --live
npm --prefix frontend run eval -- a8 --phase dev --run a8-open-v1 --live
npm --prefix frontend run eval -- a8 --phase smoke --run a8-open-v1 --live
npm --prefix frontend run eval -- a8 --phase pilot --run a8-open-v1 --live
npm --prefix frontend run eval -- a8 --phase test --run a8-open-v1 --live
npm --prefix frontend run eval -- a8 --phase report --run a8-open-v1
```

`a8-open-v3` продолжает v1 и v2, а не начинает заново. `--from` задаётся один раз на preflight и закрепляется в `campaign.json`; preflight берёт снимок маршрутов первого источника без сети, потому что новый endpoint меняет `provider` и hash каждого запроса. Слот из источника переиспользуется только под точным ключом с hash полного запроса (модель, маршрут, промпт, caps, decoding). Ответ берётся как есть, в том числе неверный. Слот, исчерпавший обе попытки, переносится как отказ. Остальные слоты вызываются снова, и уже потраченные на них попытки входят в тот же лимит 2. Probe всегда идёт live: он проверяет, что маршруты отвечают сегодня. Расход и POST источников входят в тот же потолок $60 / 4000 и показываются в отчёте отдельно.

Stage 2 и председатель видят ответы в порядке завершения вызовов; переиспользованные идут первыми в порядке источника. Поэтому промпты Stage 2 и синтеза v1 воспроизводятся байт в байт. Правила рук записаны в `campaign.json`: A8 требует все три ответа Stage 1, S8 — все пять генераций с текстом, иначе рука считается отказом метода. В v1 S8 сводил любые непустые генерации, поэтому v1 и v3 — не один протокол.

Внутри вопроса Stage 1 и четыре генерации B идут параллельно, затем параллельно ветки A8 (Stage 2 → синтез) и S8. `--jobs` (по умолчанию 6) вопросов идут сразу, `--in-flight` ограничивает HTTP всего прогона (по умолчанию jobs × 7), `--model-in-flight` — одной модели (по умолчанию 6). Вопрос в cooldown остаётся pending, остальные продолжают. Пауза сети или in-flight бюджета ключа не завершает процесс: он ждёт и делает следующий проход, до `--max-resumes` (по умолчанию 30). Нехватка кредита, ключ, потолок трат и fatal завершают фазу кодом 2 или 1.

```text
npm --prefix frontend run eval -- a8 --phase preflight --run a8-open-v3 --from a8-open-v1,a8-open-v2
npm --prefix frontend run eval -- a8 --phase probe --run a8-open-v3 --live
npm --prefix frontend run eval -- a8 --phase dev --run a8-open-v3 --live
npm --prefix frontend run eval -- a8 --phase smoke --run a8-open-v3 --live
npm --prefix frontend run eval -- a8 --phase pilot --run a8-open-v3 --live
npm --prefix frontend run eval -- a8 --phase test --run a8-open-v3 --live
npm --prefix frontend run eval -- a8 --phase report --run a8-open-v3
```

`a8-open-v4` проверяет, что именно потерял конвейер в v3. Там 155 из 360 ответов судей упёрлись в лимит 4096 токенов, 81 не дошёл до строки `FINAL RANKING`, а синтез A8 обрезался на 8192 токенах в 22 вопросах против 13 у S8; все обрезанные ответы получили ноль. В v4 лимиты Stage 2 и обоих синтезов задаются на preflight флагами `--stage2-cap` и `--final-cap` и закрепляются в `campaign.json`; лимит Stage 1 и генераций B не меняется, поэтому эти слоты берутся из v1–v3 по hash запроса, а Stage 2 и синтезы вызываются заново. Дедлайн потока растёт вместе с самым большим лимитом (`streamTimeoutSeconds`, из расчёта 8 токенов в секунду плюс 120 с на заголовки), иначе движок обрывал бы длинный ответ по своим 600 с. Дедлайн не входит в тело запроса и в hash. Preflight отказывает, если какой-то маршрут не может выдать новый лимит. Источник с другими лимитами допускается: разница записывается в `campaign.json` (`sourceDifferences`), а защита от чужого слота остаётся за hash.

Новая рука P8 — большинство по трём ответам Stage 1 совета, без дополнительных вызовов; ответ без разбираемой последней строки воздерживается, ничья решается seeded hash, как A4 в `main`. Правило неполного состава у P8 то же, что у A8. Primary-пара прежняя: A8 против S8. Пары P8 против S8 и P8 против A8 вторичные, с одной поправкой Холма на семью; они не заменяют основной вывод. В v3 такое большинство дало бы 103 из 120, столько же, сколько S8.

```text
npm --prefix frontend run eval -- a8 --phase preflight --run a8-open-v4 --from a8-open-v1,a8-open-v2,a8-open-v3 --stage2-cap 16384 --final-cap 16384
npm --prefix frontend run eval -- a8 --phase probe --run a8-open-v4 --live
npm --prefix frontend run eval -- a8 --phase dev --run a8-open-v4 --live
npm --prefix frontend run eval -- a8 --phase smoke --run a8-open-v4 --live
npm --prefix frontend run eval -- a8 --phase pilot --run a8-open-v4 --live
npm --prefix frontend run eval -- a8 --phase test --run a8-open-v4 --live
```

### a8-open-v5: общий максимальный лимит, новые блоки, защита от цикла

v5 — отдельная кампания со своим бюджетом. Она берёт у v4 только снимок маршрутов (`--routes-from a8-open-v4`): ни один слот не переиспользуется, расход v1–v4 не переносится. Потолок задаётся на preflight (`--max-usd 100 --max-posts 6000`) и потом не меняется.

Кампания `a8-open-v5` остановилась на probe: OpenRouter отклонил отозванный ключ (HTTP 401 на всех маршрутах, $0, 5 POST), а постоянную паузу `auth` тогда нечем было снять. Она сохранена как прерванная запись. Затем `a8-open-v5b` прошла preflight и probe ($0.27). Probe показал, что StepFun выдаёт около 23 токенов в секунду против 128–422 у остальных маршрутов, а на вопросе ArXivMath все пять маршрутов дошли до лимита 32768 без ответа. ArXivMath по решению пользователя отложен: при потолке $100 он один стоил бы около $37 и не дал бы пройти шлюзу pilot. Затем `a8-open-v5c` с блоками rgym, amc, hmmt и livemath прошла dev и smoke, но pilot встал. Маршрут hy4 ответил 32 раза upstream 429, и вскрылись три ошибки: вопрос ждал вечно, если его вызов на поздней стадии был пропущен по охлаждению, а охлаждение уже кончилось; два отказа 429 исчерпывали обе попытки слота и делали его окончательной ошибкой; резерв отказа держался целиком. Ещё на dev провайдер StepFun отклонил 29 из 36 вызовов «temporarily at capacity», и протокол счёл их неверными ответами. v38 исправляет это, а измерение идёт под `a8-open-v5d` с теми же блоками, протоколом, банком и потолком. ArXivMath остаётся в банке для отдельной кампании.

`a8-open-v5d` закончила основную часть (151 из 151), но в ней осталось пять сбоев инфраструктуры, а не метода:
- Три вопроса закрылись с неполным советом. Вызов hy4 на Stage 1 пропускался по охлаждению. На следующем проходе рантайм вернул сохранённый пропуск, не обновив его время. Пока шёл медленный StepFun, охлаждение кончилось, и вопрос закрылся, ни разу не спросив hy4.
- Одну генерацию B провайдер оборвал после 331 с потока («Stream ended before [DONE]»). Ошибка внутри потока стала окончательной, хотя у слота оставалась вторая попытка.
- Ещё одну генерацию B оборвал перезапуск раннера, и обрыв засчитался как попытка. Этот слот закрыт ручной поправкой.

v39 исправляет четыре места рантайма:
- пропуск во время охлаждения пишется заново, со свежим временем, и держит вопрос;
- исчерпание попыток проверяется раньше охлаждения;
- POST, который не дал ответа при оставшейся попытке, ждёт следующего прохода; окончательно может упасть только последняя разрешённая попытка;
- POST, который раннер начал и не закрыл, не считается попыткой ни в своей кампании, ни в источнике повтора. Отказы до генерации в источнике тоже не считаются.

Запросы от этого не меняются. Поэтому `a8-open-v5e` (`--from a8-open-v5d`) переиспользует каждый слот v5d с тем же запросом и вызывает заново только недостающие. Источник обязан совпадать с ней по маршрутам, банку, блокам, лимитам, профилю и потолку. Расход и POST v5d входят в тот же потолок $100 / 6000 POST, а отчёт считает деньги и счётчики по обеим кампаниям. Неразобранный ответ на лимите 32768 — ответ модели при заданном лимите; он не повторяется и считается неверным.

**Вопрос.** Как различается точность двух замороженных конвейеров, A8 v5 и S8 v5, на выбранной смеси новых задач при заданных лимитах, маршрутах и правилах повторов и разбора. Это сравнение полных систем. Эффект совета, разнообразия моделей, лимитов или детектора отдельно не измеряется, а один общий `max_tokens` не делает денежные и вычислительные бюджеты равными. Условия приёмки:

- **R1.** Все новые вопросы получили терминальные исходы обеих рук, и прежние вопросы не тратили бюджет раньше этого.
- **R2.** Банк, метод, правила анализа и выбор dev воспроизводимы по сохранённым файлам и хешам.
- **R3.** POST, повторы, резервы и resume не обходят пределы.
- **R4.** Незавершённые вопросы, терминальные отказы и неизвестная стоимость различаются.
- **R5.** Отчёт отвечает на основной вопрос и даёт диагностику без новых вызовов модели.

**Заморозка метода.** Хеш исходников покрывает все локальные модули, которые загружает `a8.js`, прямо или через другие модули; тест следит, чтобы список совпадал с реальным замыканием импортов. Preflight v5 отказывает, если какой-то из этих файлов изменён или не закоммичен, и записывает коммит в `campaign.json` (`gitHead`). Поэтому код коммитится до preflight, а все фазы, кроме report и loops, сверяют хеш. Правка метода после preflight — новая версия кампании.

**Лимиты.** `--caps max` ставит один лимит на все стадии: самый большой, который выдерживает каждый маршрут шортлиста. Это `min(maxCompletion, (context − 8000) / 6)`, сегодня 32768 (StepFun). Лимит генераций B всегда равен лимиту Stage 1: первый ответ B — это sample 1. Дедлайн потока растёт до 4216 с.

Контекст проверяется дважды. Preflight отказывает, если синтезу S8 (`6 × лимит + 8000`) или судье (`5.5 × лимит + 8000`) не хватает контекста какого-то маршрута; это предварительная проверка, а не гарантия. Перед каждой отправкой оценка собранного промпта плюс `max_tokens` сверяется с контекстом маршрута. Оценка — 2 символа на токен плюс запас; на тексте с иероглифами она может занизить число токенов. При превышении вызов отказывает с причиной `context`, текст и лимит не урезаются. Отказ провайдера по контексту считается отказом метода.

Probe подтверждает, что маршрут принимает запрос с `max_tokens` 32768: завершённый поток с `usage`, а не только HTTP 200. Что модель способна дописать до 32768, он не проверяет. В v5 probe не заменяет маршрут сам. Пока лимит не подтверждён на всех маршрутах, probe не считается законченным и dev не стартует. Повторный запуск probe опрашивает только неподтверждённые маршруты, новой попыткой того же запроса. Если маршрут отвечает 400 или 404, лимит этой кампании ему не подходит; лимиты фиксируются на preflight, поэтому нужна новая кампания с явными флагами лимитов.

**Попытки и POST.** На слот приходится не больше двух попыток, дошедших до провайдера, вместе с повторами после цикла, сети и 429; счётчик сохраняется после resume. Отказ 402 «кредит на запросы в полёте» бесплатен и случается до провайдера. Транспорт повторяет такой POST один раз за запуск слота; это не попытка модели, но POST входит в предел кампании, а отчёт его показывает. Второй такой отказ в том же запуске ставит кампанию на паузу. Пауза из-за ключа, лимита ключа или баланса (`auth`, `key_budget`, `insufficient_funds`) переживает перезапуск и снимается в начале следующей фазы, только если OpenRouter показывает, что причина устранена: ключ отвечает 200, у ключа остался лимит или на счёте есть деньги. Доказательство пишется в журнал бюджета; непонятный отказ оплаты (`payment_unknown`) ждёт человека. С учётом resume на слот приходится не больше четырёх физических POST. Нулевую стоимость получают только классифицированные отказы до провайдера; неизвестный 402 не освобождается.

Отказ по мощности — upstream 429 или ошибка в потоке вроде «temporarily at capacity» без единого символа ответа — тоже не попытка модели. Слот ждёт охлаждения маршрута (из Retry-After у 429, 2 минуты у ошибки в потоке) и спрашивается снова; такой POST стоит $0, но входит в предел POST. Вопрос ждёт, только если его вызов пропущен в этом проходе или маршрут ещё охлаждается; старый пропуск с истёкшим охлаждением вопрос не держит, и стадия спрашивает вызов заново. Нагрузка провайдера поэтому задерживает ответы, но не превращает их в отказы метода.

**Защита от цикла.** Опция движка `loopGuard` по умолчанию выключена, продукт её не включает. Она сравнивает последние 4000 символов рассуждения с 24000 символами перед ними по шинглам длиной 40. Проверки идут на фиксированных позициях накопленного текста, 6000, 8000 и дальше через 2000, и каждая пересечённая позиция проверяется, поэтому срабатывание и его позиция не зависят от того, как сеть порезала поток. Срабатывание — 80% совпадений на двух проверках подряд. У рассуждения и видимого текста отдельные детекторы; канал рассуждения закрепляется за первым появившимся (провайдеры дублируют его в `reasoning` и `reasoning_details`).

Первая зациклившаяся попытка отменяется и повторяется один раз; если зациклилась и последняя, её накопленный текст сохраняется с пометкой `loopCut` и оценивается как написан. Сохранённый текст — всё прочитанное до конца той дельты потока, на которой сработал детектор. При другом разбиении потока он может отличаться, и такая добавка может изменить последнюю строку, разбор судьи и пересылаемый хвост. Позицию срабатывания и длину сохранённого текста показывает `a8 --phase loops`. Польза раннего прерывания этим прогоном не доказывается.

Прогон по сохранённым SSE v3 и v4 через тот же парсер: судьи v4 — 20 из 51 обрезанных и 4 из 309 дописанных (настоящие циклы, которые сами закончились через 7–16 тыс. токенов), судьи v3 — 5 из 107, синтезы — 2 из 39, Stage 1 — 1 из 42, генерации B — 0; на дописанных Stage 1, генерациях и синтезах — 0.

**Хвостовое правило.** Ответ, оборванный лимитом или детектором до видимого текста, передаётся судьям, председателю и в синтез S8 как пометка и последние 8000 символов его рассуждения. Судья, оборванный до видимого текста, разбирается заново из такого хвоста с исходными метками, поэтому ранжирование, оценки, замечания и спорные утверждения из отброшенного начала не доходят ни до агрегата, ни до председателя. Дописанные ответы идут целиком. Все оценки читают исходный сохранённый текст. Это отличает v5 от продукта и от v4.

Происхождение данных. Строки Hugging Face скачиваются один раз и замораживаются в `.cache/raw`. Воспроизводимость даёт хеш замороженного файла; записанный при загрузке sha репозитория не доказывает, что файл соответствует этой ревизии. LiveMathBench взят из зеркала, пока его тождество с оригиналом не проверено. Экземпляры reasoning-gym новые, но генераторы публичны.

Числовое подмножество — задачи, чей эталон читается как одно целое или несократимая дробь; правило смотрит только на эталон. Это не весь исходный бенчмарк: отчёт показывает охват каждого источника и причины исключений. Вид ответа `number` канонизирует целые любого размера и дроби через BigInt; инструкции для `integer` и `choice` не менялись. Строгое чтение берёт только последнюю непустую строку `ANSWER:`. Инструкция вида `number` сообщает модели, что ответ одно рациональное число; в семи задачах ArXivMath условие допускает +∞, и инструкция этот вариант исключает. Подсказка одинакова для всех рук, но абсолютная точность поэтому не сравнима с таблицами MathArena.

Эталоны reasoning-gym. Все 64 строки проверены независимо, без ответов моделей. `self_reference` проверен перебором наборов истинности. `binary_alternation`, `lcm`, `aiw` и `number_sequence` проверены кодом; у последовательностей это ещё и проверка неоднозначности по фиксированному списку простых правил. `gsm_symbolic` и головоломка `aiw` с коллегами решены вручную до просмотра эталона. Запись по каждой строке — в `.cache/manual/rgym-verify.json`; без неё `prepare` банк не строит. Исключены пять строк test, без замены:

- три вопроса `aiw` о человеке, которого нет в условии (`ambiguous`);
- головоломка `aiw` с коллегами, где эталон 8 противоречит условию, верно 7 (`wrong_gold`);
- вопрос `gsm_symbolic`, где выходит 60.8 ученика (`inconsistent`).

Раньше, до первого вызова модели, исключено семейство `simple_geometry` (противоречивые «выпуклые» многоугольники), а `number_sequence` получает не меньше шести членов.

Прочие исключения и пометки. Эталоны AMC проверены вручную или перебором; задачи, которым нужен рисунок, не взяты. В пяти задачах AMC (12A #2, #10, #14, #16, #22) рисунок убран или переписан текстом; они помечены `adapted`, и отчёт показывает основной результат ещё и без них. HMMT February 2026 #32 исключена: она просит все возможные значения и велит записать список в `\boxed`, что спорит со строкой `ANSWER` с одним числом. Все исключения по имени собраны в `MANUAL_EXCLUSIONS` и входят в хеш метода.

**Что сравнивается.** Основная пара — A8 против S8 на пяти новых блоках, по каждому вопросу с весом 1/N. Семья Холма из ровно четырёх сравнений: A8 − S8 в группе A, A8 − S8 в группах B и C вместе, A8 − P8 и S8 − P8 на всём новом наборе. Пустое подмножество остаётся в семье с p = 1, чтобы поправка не ослабла. Прежние 120 вопросов — регрессионная проверка вне семьи: по ним четыре раза выбирали лимиты, и поправка на множественность этого не лечит.

Группа хронологии считается по самой ранней известной дате материала против дат листинга выбранных моделей: A — после всех или сгенерировано, B — после части, C — до всех, Unknown — дат не хватает. Unknown остаётся в основном наборе, но не входит ни в A, ни в B и C. Месяц из arXiv-идентификатора — месяц первой версии статьи. Тот же месяц, что листинг, считается «не после»; это осторожность в одну сторону, а не дата отсечения знаний. Состав групп известен после dev, потому что зависит от выбранного совета; H всегда входит в совет. При совете v4 группа B — один месяц ArXivMath, слишком мало для отдельной проверки, поэтому в семье она объединена с C; при совете без GLM B может оказаться пустой. Без ArXivMath группа B пуста при любом совете, и второе сравнение семьи идёт по группе C. В группу A попали только reasoning-gym и AMC, так что разница между группами смешивает свежесть с типом задач. Ни одна группа не объявляется свободной от утечки.

**Чтение результата.** Каждый вопрос получает свой ответ:

- **Направление** — точный McNemar: при p < 0.05 знак Δ, иначе направление не установлено. Приоритет у McNemar.
- **Выигрыш больше 5 пп** для каждой руки — по 95% интервалу. Он поддержан, если граница интервала за порогом, и не поддержан, если интервал целиком по эту сторону порога. Граница, равная порогу, критерий не проходит.
- **Практическая эквивалентность в ±5 пп** — 90% интервал строго внутри. Это приближённый bootstrap-критерий, а не точный TOST.

Оба интервала считаются одним парным bootstrap внутри блоков, 10 000 повторов. Вырожденный интервал не даёт выводов о размере и эквивалентности. Число расходящихся пар печатается; при малом числе есть оговорка о приближённости. p ≥ 0.05 не читается как равенство.

Мощность точного McNemar для выигрыша +5 пп при 151 вопросе — 40.8% при 10% расходящихся пар и 21.6% при 20%; для 80% нужно около 340 и 660 вопросов. Это мощность обнаружить отличие от нуля, а не доказать выигрыш больше 5 пп. Отрицательный результат вероятно оставит вопрос открытым и при реальном выигрыше 5 пп. Выборку после результата не увеличивать. Одна поправка эталона меняет Δ не больше чем на 2/N, около 1 пп.

**Завершённость и порядок.** Test сначала завершает все новые вопросы; первый прежний вопрос уходит только после этого, и пауза или остановка основной части прежние не запускает. Основной вывод окончателен, когда у каждого нового вопроса есть терминальные исходы обеих рук, даже если прежние блоки не завершены. При неразрешённых резервах точность окончательна, а деньги предварительны. Терминальный отказ метода считается неверным ответом; незавершённый вопрос не оценивается и нулём не становится. Кампании v1–v4 сохраняют прежний порядок.

**Диагностика без новых вызовов.** Отчёт показывает:

- macro по блокам и A8 − S8 при исключении каждого нового блока по очереди;
- мягкое чтение (`LENIENT_RULES`) сохранённых финальных текстов A8, S8 и B8; P8 мягко не перечитывается, потому что его бюллетени хранят только строгие ответы;
- основную пару без адаптированных задач AMC;
- механизмы на новых блоках:
  - P8 — plurality по трём каноническим ответам Stage 1 совета; ничья разбивается сидированным хешем по вопросу, неразобранный ответ воздерживается, без допустимых ответов — отказ;
  - голос пяти генераций B по тому же правилу и лидер Stage 2;
  - исправления и порчи председателя против лидера и синтеза S8 против голоса пяти генераций;
  - oracle@3 совета против oracle@3 генераций B 1–3; ответ B 1 входит в оба набора;
- таблицу dev: B — лучший из проверенных кандидатов на этом dev по зафиксированному правилу, а не доказанно лучший для смеси test; в dev 24 прежних вопроса из 40;
- счётчики стадий. Остановка по длине раньше лимита — сигнал проверить урезание у провайдера, а не доказательство: в v4 все 63 такие остановки пришлись ровно на лимит. Там же повторы после отказа 402;
- стоимость: подготовительные фазы отдельно от test; в самостоятельной стоимости общий ответ B 1 входит в обе руки; вывода об эффективности при равном бюджете нет.

**Pilot и шлюз.** Pilot берёт по два dev-вопроса на блок из семи блоков с dev в заранее заданном порядке. Стоимость pilot-вопроса — все его вызовы сравнения и повторы: известная цена фактическая, неизвестная — удерживаемым резервом. Вызовы dev на тех же вопросах не считаются. Для блока базовый прогноз — среднее, стресс-прогноз — max(1.5 × среднее, самый дорогой вопрос); 1.5 — заранее выбранное допущение, не квантиль и не гарантия. Так же для POST. AMC без pilot-вопросов берёт максимум среди всех блоков с pilot отдельно для базы и для стресса.

Прогнозов два: только основная часть и основная плюс прежняя. Допуск к test даёт стресс-прогноз основной части против остатка. Если прежняя часть не помещается, test всё равно стартует, а прежние вопросы идут после основных в пределах остатка. Перед расчётом идёт бесплатный `reconcile`. Если допуск не получен, pilot расширяется один раз до четырёх вопросов на блок, и только когда базовый прогноз основной части помещается в остаток за вычетом ожидаемой стоимости расширения; иначе он останавливается с расчётом недостатка. Формула, допущение, наблюдения и резервы пишутся в `forecast.json`. Test не стартует без пройденного шлюза, если не передан `--accept-forecast`.

**Темп.** Флаги `--jobs`, `--in-flight` и `--model-in-flight` задают только темп и в хеш метода не входят. Узкое место — модель B = H: на неё приходятся 8 из 12 вызовов вопроса, и в начале вопроса она получает пять вызовов сразу. В v4 при 12 вопросах и 12 вызовах на модель вызовы StepFun ждали места в очереди с медианой 35 с, это четверть их времени; DeepSeek и GLM не ждали ни разу, ответов 429 не было ни в v3, ни в v4. Провайдеры ограничивают мощность сами: в v5c маршрут hy4 (общий пул Cohere) дал 32 ответа 429 при 40 потоках, а StepFun (Featherless) отклонял вызовы уже при 36. Поэтому test и pilot идут по 24 потока на модель, dev — по 12, чтобы медленный StepFun не упирался в предел; общий лимит HTTP по умолчанию равен 7 × число вопросов и покрывает пик. `--max-resumes` поднят, потому что каждое охлаждение — это ещё один проход. Резерв одного вызова StepFun при лимите 32768 — около $0.11, так что даже 60 вызовов в полёте держат около $7 и бюджет не тормозит. Остающаяся задержка внутри вопроса — общий барьер после Stage 1 и генераций B; он удлиняет вопрос, но не ограничивает пропускную способность, которую задают число вопросов и лимит на модель.

**Проверка циклов перед test.** `a8 --phase loops --of pilot` восстанавливает каждую остановку детектора по сохранённому телу потока: модель, стадию, позицию, долю повтора, итог слота и текст перед остановкой. Список пишется в `reports/loops-pilot.json`. Каждую остановку человек читает до test; остановка на тексте, который не зацикливался, останавливает кампанию. Фаза ничего не отправляет и может идти рядом с работающей фазой. Точность pilot метод не меняет.

**Расход.** Прерванный поток не приносит `usage`, и его резерв остаётся удержанным. Каждая попытка сохраняет `generationId`; `a8 --phase reconcile` спрашивает OpenRouter фактическую стоимость через `/api/v1/generation` и заменяет резерв ею, один раз. Неизвестная стоимость не становится нулём. В начале каждой фазы reconcile идёт сам, а счётчик ключа пишется как аудит, без влияния на резервы. `--self-test` один раз намеренно обрывает короткий вызов на маршруте B и проверяет, что его цена находится. Это платный вызов, поэтому он требует `--live`, и нужен он, только если ни одна прерванная попытка ещё не получила цену.

**Эталоны после прогона.** Официальный ключ MAA применяется ко всем задачам AMC через `report --gold-overrides <file>`. Спорный эталон решается по условию, не глядя на исходы рук. Сохранённые ответы переоцениваются без новых вызовов, строгий разбор не расширяется, и рядом с исходным отчётом пишется `report-corrected.md`. Просмотренный test v5 не станет свежим для следующих версий метода.

Известное ограничение. Модели отвечают в видимом тексте почти только строкой `ANSWER`, всё решение остаётся в скрытом рассуждении. Поэтому судьи и председатель A8 видят у дописанных ответов голые ответы без решения.

```text

npm --prefix frontend run eval -- a8 --phase reconcile --run a8-open-v5d
```

`complete` запускается после repair на все 120 вопросов. Однозначный ответ, записанный не в строгом формате (жирный `ANSWER`, скобки, `\boxed{}`, строка `ANSWER` не последняя, последняя строка «the answer is X»), читается из уже полученного текста и не запрашивается снова. Stage 2, red team и Stage 3 повторяются из журнала repair без новых вызовов: новый розыгрыш Stage 1 меняет только оценку ячеек, которые его читают. Результат пишется в `frontend/eval/.runs/<id>/complete/` и не меняет as-run и repair. `--max-usd` по умолчанию 20, `--max-posts` по умолчанию 600, `--jobs` по умолчанию 4. `--cooldown-seconds` ограничивает паузу после upstream 429 (без флага остаётся обычные 10 минут). `--deadline-minutes` держит процесс живым и повторяет охлаждённые ячейки до абсолютного срока, записанного в state; после срока ячейка, которую провайдер всё ещё не отдаёт, считается неверной с пометкой provider unavailable, а голос A4 собирается из остальных ответов.
