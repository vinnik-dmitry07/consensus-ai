# Платный консилиум против сильного Self-MoA

## 1. Цель

Ответить на вопрос:

> Даёт ли консилиум из сильных платных моделей лучший результат,
> чем несколько ответов одной сильной модели с последующим синтезом,
> и каких дополнительных ресурсов это требует?

Первый профиль фиксирует три модели консилиума.
Это ограничение первого эксперимента, а не утверждение об оптимальном размере.

Отрицательный результат этого профиля не исключает пользу совета
из пяти или восьми моделей.

Исследованный репозиторий:
- vinnik-dmitry07/consensus-ai
- master
- commit: 2df7e17813687d0a40411e54ad5e8c57e1786ca0

Перед реализацией проверить актуальный HEAD и применимые инструкции.
Не откатывать пользовательскую ветку на исследованный commit.

## 2. Требования

| ID | Требование | Критерий |
|---|---|---|
| R1 | Проверять сильный платный состав | Есть основания выбора участников; наличие free-двойника не требуется |
| R2 | Сравнить методы непосредственно | Новые A8 и S8 выполняются на одинаковых вопросах с одним H |
| R3 | Соблюсти общий бюджет | Все фазы, повторы и незавершённые запросы входят в одну кампанию |
| R4 | Сохранить воспроизводимость | Зафиксированы код, параметры, маршруты, данные и происхождение результатов |
| R5 | Начать измерения рано | Первый платный probe не ждёт полной сборки A8/S8 и отчётной системы |
| R6 | Сделать ограниченный доказательствами вывод | Исторические 120 вопросов считаются exploratory; автоматического внедрения нет |

## 3. Сравниваемые варианты

Обозначения:
- B — лучшая среди проверенных конфигураций на dev.
- H — председатель; в первом профиле H = B.
- «Конфигурация» включает model ID, маршрут, reasoning и decoding options.

| Вариант | Выполнение | Назначение |
|---|---|---|
| B8 | Первый заранее определённый ответ B | Одиночный baseline |
| S8 | Пять отдельных генераций B → H | Self-MoA baseline |
| A8 | Три разных модели → Stage 2 → H; без red team | Проверяемый консилиум |

Для A8:
- n_samples = 1.
- top_k = 3.
- self-exclusion включён.
- Три разных vendor.
- Анонимизация, shuffle, Borda и промпт синтеза соответствуют текущему A7.
- red_team = null.

Для S8:
- Использовать существующую логику промпта A3.
- Первый ответ B переиспользуется из Stage 1 A8.
- Ещё четыре ответа — отдельные логические вызовы.
- Тот же H и тот же лимит финального ответа, что у A8.

Пять отдельных запросов не объявлять пятью независимыми источниками ошибок.

Диагностика без дополнительных модельных вызовов:
- Голосование по ответам A8.
- Голосование по пяти ответам B.
- Корректность лидера Stage 2.
- Наличие правильного ответа среди исходных кандидатов.
- Исправление и порча ответа при переходе leader → final.
- Совпадение текстов и ответов между генерациями.

Номинально на один новый вопрос:
- A8 отдельно: 3 + 3 + 1 = 7 вызовов.
- S8 отдельно: 5 + 1 = 6 вызовов.
- Совместный эксперимент: 3 + 4 + 3 + 2 = 12 вызовов.
- B8 и диагностические оценки новых вызовов не требуют.

Это сравнение полных методов при заданных ограничениях.
Оно не изолирует чистый эффект разнообразия и не является
сравнением при доказанно одинаковом compute.

Resume и новый дочерний каталог не обнуляют расходы.

Полное завершение 120 вопросов в пределах $60 заранее не гарантируется.

## T03. Связать request policy с реальным POST

Файлы:
- frontend/eval/runtime.js.
- frontend/src/engine/browser/openrouter.js.

- frontend/eval/contract.test.js.

Runtime:
1. Добавить опциональные requestPolicy и retryLimit в createSession.
2. Рассчитывать effectiveOptions до canonicalCompletionRequest.
3. Хешировать запрос с effectiveOptions.
4. В execute передавать те же options.
5. Количество оставшихся попыток рассчитывать с учётом journal.
6. Не применять overrides только после вычисления requestHash.

Canonical request:
- Поддержать явно переданные provider, reasoning и decoding options.
- maxTokens уже поддерживается: переиспользовать существующий механизм.
- Без новых options сохранять старый payload.
- Не менять глобальные product defaults.

Для каждой стадии проверять:
- Разрешённый logical slot.
- Ожидаемую модель.
- Маршрут.
- Token cap.
- Reasoning/decoding.
- Совпадение canonical request и фактического POST body.

Один logical slot получает один requestHash.
Изменённый запрос не должен появляться как новая попытка того же слота
под прикрытием другого hash.

Председатель:
- Добавить опциональный strictChairman для eval.
- При нём H не заменяется другим участником.
- Недоступность H даёт обычный terminal failure соответствующего arm.
- Product fallback без этой опции сохраняется.

Нарушение эксперимента:
- Ввести типизированную EvalInvariantError.
- Не превращать её в failResult или provider_error.
- Провести её через catch в runModelAttempt и вызывающих функциях.
- Установить общий fatal-флаг кампании, запрещающий новые POST.
- Уже начавшиеся запросы завершить или отменить с сохранением учёта затрат.

Готово, когда тесты доказывают:
- Записанный canonical request равен отправленному body.
- Реальные caps равны заданным, включая reasoning-конфигурации.
- Запрещённая модель/роль/маршрут не достигают сети.
- Нарушение hash/body завершает кампанию как fatal.
- Оно не засчитывается как неверный ответ модели.
- Старые вызовы без eval options сохраняют поведение.

## T04. Реализовать общий бюджет кампании

Файлы:
- frontend/eval/budget.js.
- frontend/eval/transport.js.
- frontend/eval/runtime.js.
- frontend/eval/budget.test.js.
- frontend/eval/contract.test.js.

Транспорт:
1. Добавить rejectFree.
2. Проверять его до сети.
3. Проверять paid allowlist, роль и request policy до сети.
4. Передавать model в бюджетную проверку каждого HTTP attempt.
5. Не использовать settings или старый allowPaid как замену paid allowlist.

Каждый HTTP attempt:
- Имеет уникальный attempt ID.
- Получает запись о резервировании до fetch.
- Расходует один POST независимо от последующего успеха.
- Учитывается отдельно от логического вызова.
- Повтор требует нового резервирования.

Условие допуска:

settled_cost + unresolved_reservations + new_reservation <= maxUsd

Одновременно должен соблюдаться maxPosts.

Резерв:
- Включает вход, выход и применимые request fees.
- Использует проверяемую верхнюю границу стоимости.
- Учитывает фактический output cap.
- Не считает отсутствующую цену нулевой.
- Учитывает применимые cache-write и long-context tiers.
- При невозможности ограничить стоимость запрос не отправляется.

Для консервативной границы входа допустимо использовать известный
max_prompt_tokens выбранного endpoint либо его context_length.
Не объявлять char_count / 4 гарантированной верхней границей.

Единицы:
- Нормализовать цены во внутреннем учёте.
- provider.max_price для prompt/completion использует $/млн токенов.
- Не переносить туда каталоговую цену за один токен без преобразования.
- Единицы дополнительных цен проверить отдельно.

Завершение:
- При наличии корректного usage.cost использовать его как фактическую стоимость.
- Не прибавлять reasoning tokens второй раз поверх уже учтённого usage.
- Освобождать неиспользованную часть резерва.
- При неизвестной стоимости, обрыве или неоднозначном network error
  сохранять консервативный резерв как unresolved.
- Не превращать missing usage в $0.
- Подтверждённое уточнение стоимости может освободить резерв,
  сохраняя историю изменения.

Временная нехватка средств:
- Если деньги удерживают работающие запросы, следующий запрос ждёт.
- После их завершения повторно проверить возможность допуска.
- Не сохранять постоянную budget pause только из-за временного резерва.
- Если работающих запросов нет и средств всё равно недостаточно,
  сохранить budget_blocked.

Resume:
- Восстанавливать расчёт из общего журнала.
- Учитывать попытки, начатые до падения процесса.
- Не освобождать неизвестные резервы автоматически.
- Не обнулять расходы при переходе к другой фазе.
- Повтор команды не повышает лимит.

Отдельно хранить:
- Фактически подтверждённые расходы.
- Сумму неопределённых резервов.
- Число POST.
- Причину остановки.

Баланс и общий счётчик ключа — диагностика.
Если ключ используется другими процессами, их разность не равна
стоимости нашего эксперимента.

Готово, когда покрыты:
- Параллельные запросы около лимита.

- После выполнения восстанавливать eval hooks и временное состояние в finally.

Готово, когда:
