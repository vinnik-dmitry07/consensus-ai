# Stay under the free-model cap

Старый сохранённый бесплатный совет больше не запускает по три samples на модель. Все бесплатные HTTP-попытки одного движка проходят общий ограничитель стартов.

## База и границы

План проверен по опубликованному [consensus-ai, commit 6cb8b5bf](https://github.com/vinnik-dmitry07/consensus-ai/tree/6cb8b5bf388d8138efca95f957b2703442858e3f). В этом снимке отсутствуют `backend/roster.py`, `ensureServableRoster`, `ensure_servable_roster`, `enqueueFree`, `run_free_call` и `_wait_free_slot`. Кнопка Top 10 Free в нём также ещё не меняет samples. Изменения, на которые опирается исходный план, могут находиться в неопубликованной рабочей ветке.

Первый шаг — найти эту базу в Cursor, прочитать её инструкции и проверить текущие callers/tests. Если предыдущие изменения отсутствуют, явно восстановить правильную базу или пересмотреть зависимости. Не воссоздавать молча исправления delisted/harness-only/reasoning-only в рамках этого изменения.

[OpenRouter документирует 20 RPM для бесплатных моделей](https://openrouter.ai/blog/tutorials/how-to-get-the-lowest-cost-llm-inference-on-openrouter/). Значение 16 — выбранный приложением запас. Один sample уменьшает число запросов; скользящее окно обеспечивает ограничение скорости. Сам по себе интервал 3 секунды не доказывает, что следующий этап обязательно получит 429.

Гарантия действует в течение жизни одного browser runtime или одного backend worker/event loop, совместно для всех его разговоров и запусков. Несколько вкладок, перезагрузка страницы, несколько workers, одновременная работа двух engine и внешние клиенты не имеют общего счётчика. Дневные квоты и provider-side 429 остаются возможны. Межпроцессная и межвкладочная координация в этот план не входит.

## Критерии приёмки

- **R1.** Непустой эффективный all-free council возвращает и сохраняет `n_samples=1`. Смешанный сохраняет запрошенное допустимое значение.
- **R2.** Settings показывает то же значение, которое использует запуск. Обычный запуск, streaming, явный `n` и Stage 1 resume не обходят ограничение.
- **R3.** Для любых последовательных бесплатных стартов `s[i] − s[i−1] >= 3s`. Для каждого старта в окне `(s[i] − 60s, s[i]]` находится не более 16 стартов.
- **R4.** Учитывается каждая HTTP-попытка, включая retry. Paid-запросы обходят free-очередь. Ожидание, отмена и ошибки не ломают дальнейшие запуски.
- **R5.** Vitest и pytest подтверждают R1–R4 на подставных часах и транспорте, без расхода OpenRouter-квоты.

## Один sample для полностью бесплатного совета

Использовать эффективный состав после существующей проверки и pruning. Бесплатность определяется по catalogue ID после удаления только поддерживаемого приложением суффикса `-reasoning` или `-reasoning-high`, затем проверкой `:free`. Не определять её по нулевой цене в каталоге и не расширять обработку aliases.

Условие — состав **непустой** и все его участники бесплатные. Пустой состав остаётся ошибкой существующей валидации. Chairman и red team не участвуют в этом условии: платный chairman не отменяет ограничение samples для бесплатных участников. Их собственные бесплатные вызовы учитывает очередь.

В найденных `ensureServableRoster` / `ensure_servable_roster` либо эквивалентных точках:

1. Получить итоговый эффективный roster и валидные настройки.
2. Для all-free состава установить `n_samples=1`.
3. Сохранить изменение, если поменялся **roster или n_samples**. Совпадение roster со старым не должно приводить к раннему возврату без сохранения samples.
4. Вернуть исправленные настройки caller, чтобы форма и запуск читали один результат.

При settings update сначала объединить patch с текущими настройками, затем проверить и нормализовать весь результат. Проверить patch только с `n_samples` и patch одновременно с `council_models` и `n_samples`. Порядок setter-вызовов не должен возвращать 3 после нормализации. Сохранять исправленный roster и samples одним существующим путём обновления, не отдельными несогласованными UI-записями. Повторная загрузка уже исправленных настроек не должна вызывать лишнее сохранение.

Известные точки интеграции:

- Browser: [frontend/src/engine/browser/engine.js](frontend/src/engine/browser/engine.js) — Settings API, `sendMessageStream`, `retryStage`; [frontend/src/engine/browser/settings.js](frontend/src/engine/browser/settings.js) — существующее localStorage-хранилище.
- Python: [backend/main.py](backend/main.py) — Settings API, обычный и streaming запуск, retries; [backend/settings.py](backend/settings.py) — объект настроек; [backend/roster.py](backend/roster.py) — только если присутствует в рабочей базе.
- Фактическое расширение Stage 1: `stage1CollectResponsesStreaming` в [frontend/src/engine/browser/council.js](frontend/src/engine/browser/council.js), `stage1_collect_responses` и `stage1_collect_responses_streaming` в [backend/council.py](backend/council.py).

Последний пункт обязателен: эти функции принимают явный `options.n` / `n`. Для all-free состава эффективное число samples остаётся 1 даже при переданном 3. Для смешанного состава существующий override сохраняется. Проверка должна завершиться до вычисления `totalSlots`, pending slots и отбора старых результатов. Resume использует существующую фильтрацию сохранённых samples с новым пределом. Предыдущие лишние samples не возвращаются в Stage 2 через этот путь.

Не создавать циклические импорты: оба OpenRouter-клиента уже импортируют settings. Разместить переиспользуемое правило в существующем безопасном слое roster либо небольшом модуле без зависимостей, если он необходим.

В проверенном Python-снимке settings — runtime singleton, без дискового сохранения. Использовать механизм рабочей ветки. Не заявлять сохранение между рестартами и не добавлять новую систему хранения. В браузере проверить запись localStorage и чтение после сброса кэша настроек.

- При ручном переходе к all-free составу и при Top 10 Free показывать 1 и блокировать изменение samples. Сохранять пользовательское редактирование через обычный Save.

- Использовать значение, возвращённое сохранением. Сохранить существующую проверку `loadedFrom` / выбора engine, чтобы форма одного engine не переписала другой.

## Общее окно бесплатных стартов

Расширить существующие очереди в:

- [frontend/src/engine/browser/openrouter.js](frontend/src/engine/browser/openrouter.js): `enqueueFree` и retry-цикл `queryModelResult`;
- [backend/openrouter.py](backend/openrouter.py): `run_free_call` / `_wait_free_slot` и retry-цикл `query_model_result`.

Имена очередей относятся к заявленной рабочей базе. Подтвердить их на первом шаге.

Одна история стартов на весь free-планировщик. Не создавать отдельные лимиты на модель, стадию, conversation или run и не очищать историю при переходе к Stage 2 или chairman. Платные вызовы не ждут free lock и не изменяют эту историю. GET каталога, credits и key не являются chat-попытками.

Для каждого бесплатного HTTP POST:

1. Проверить отмену.
2. По монотонным часам удалить timestamps `<= now − 60s`.
3. Рассчитать ближайшее допустимое время как максимум текущего времени, `lastStart + 3s`, `oldestStart + 60s` при заполненном окне, действующего общего cooldown и срока retry backoff.
4. Если нужно ждать — дождаться и заново проверить все условия. Не складывать независимые сроки ожидания и не выдавать заранее будущие timestamps.
5. Атомарно повторно проверить доступность и зарегистрировать фактический старт непосредственно перед вызовом транспорта. Между выдачей допуска и началом `fetch` / `client.post` не должно быть другого асинхронного ожидания.

Начальный `lastStart` отсутствует, а не равен нулю: первый запрос при пустой истории допускается сразу.

Использовать `performance.now()` / `time.monotonic()` либо эквивалент рабочей базы. Не смешивать их с wall-clock timestamps. HTTP-date из Retry-After преобразуется существующим parser в длительность; затем используется срок ожидания на монотонных часах.

Разделить короткую критическую секцию проверки/регистрации и ожидание сети. Если существующая очередь дополнительно сериализует целые free-вызовы, сохранить этот предел конкурентности: добавление окна не должно незаметно увеличивать её. Повторная попытка не должна вставать за собственным незавершённым элементом очереди и ждать его освобождения.

## Retry, отмена и lifecycle

Каждая повторная HTTP-попытка получает новый допуск. Одного admission вокруг всего `queryModelResult` / `query_model_result` недостаточно.

Все бесплатные вызовы через эти клиенты используют одну историю: Stage 1, Stage 2, red team, chairman, retries и title, если его модель бесплатная. Текущий title model в проверенном снимке платный. Менять выбор модели не требуется.

Сохранить существующий `free-models-per-min` cooldown, классификацию ошибок, Retry-After parser и число попыток. После пробуждения учитывать возможное продление общего cooldown другим запросом. Не сбрасывать историю стартов после 429.

Отмена до отправки не расходует слот и не блокирует следующие элементы. После начала transport-вызова timestamp остаётся, даже если пришла ошибка, timeout или отмена: попытка уже могла дойти до провайдера. Отдельный request timeout начинается при dispatch, а пользовательская отмена действует и во время очереди. Ошибка одного запроса не должна оставлять rejected promise tail или занятый lock.

История общая для запусков в одном runtime. В тестах сбрасывать limiter вместе с timer mocks и настройками. Не переносить asyncio lock/waiters между закрытыми тестовыми event loops.

## Проверки

Дополнить существующие `openrouter.test.js`, `engine.test.js`, тесты Stage 1, [backend/test_openrouter_errors.py](backend/test_openrouter_errors.py), [backend/test_settings_models.py](backend/test_settings_models.py) и подходящие тесты retries. Отдельный `backend/test_free_limits.py` допустим как новый файл, если так проще изолировать подставные часы.

- Сохранённый all-free council, samples=3, roster неизменен: Settings load возвращает 1; значение действительно записано; повторное чтение даёт 1.
- Частичный patch samples=3 и совместный patch roster+samples=3: all-free результат и хранилище равны 1; mixed результат остаётся 3.
- Reasoning-варианты; pruning оставляет только free; пустой roster: правило работает по нормализованному непустому составу; пустой не становится допустимым.
- Запуск, явный n=3, streaming и Stage 1 resume: один фактический slot на участника; старые лишние samples не сохраняются в возобновлённом Stage 1.
- Платный chairman или red team при all-free участниках: samples остаётся 1; платный вызов не занимает free-слот.
- 18 конкурентных бесплатных вызовов разных моделей, мгновенный mock transport: старты 0, 3, …, 45; 17-го нет при 59.999; он допускается при 60; 18-й не раньше 63 секунд.
- Более 32 попыток и пауза дольше минуты: обе инварианты R3 для всей истории; после простоя нет лишнего ожидания старого окна.
- 429 и общий cooldown: каждая попытка учитывается; выполняется наиболее поздний срок; уже ожидающий запрос перечитывает продлённый cooldown.
- Paid-запрос при заполненном free-окне: transport вызывается сразу, не дожидаясь free-очереди; paid-попытка не занимает её слот.
- Отмена до и после dispatch и ошибка транспорта: до dispatch нет вызова и timestamp; после dispatch запись сохраняется; очередь продолжает работать.

Проверять timestamps транспортных вызовов, а не только вызовы sleep или длину внутреннего списка. Для точного расписания ответы мгновенные и cooldown отсутствует. При медленных ответах допустимы более поздние старты.

Vitest уже настроен для Node и не имеет DOM test dependencies. Проверить переиспользуемое правило и persistence автоматически. Форму пройти вручную в browser и local режимах. Не добавлять DOM-инфраструктуру только ради текста подсказки. Python-тесты используют `unittest.IsolatedAsyncioTestCase`. Они запускаются через pytest без `pytest-asyncio`.

Команды из корня репозитория после реализации:

```bash
npm --prefix frontend test
npm --prefix frontend run build
uv run --with pytest python -m pytest backend
```

В проверенном `pyproject.toml` pytest не объявлен. `--with pytest` предоставляет test runner без изменения production-зависимостей. Если рабочая ветка уже содержит установленный test runner, использовать её штатную команду.

Тесты выполняются с mock transport, без live smoke-запросов. Перед завершением записать фактический HEAD, команды и результаты. Этот документ не является подтверждением прохождения тестов.

## Когда пересмотреть план

- В рабочей ветке нет заявленных roster/queue исправлений: сначала определить корректную базу и зависимости.
- `run_free_call` удерживает очередь вокруг всего retry-цикла: сначала определить безопасную границу admission, чтобы не получить self-deadlock.
- Требуется общий лимит между вкладками, workers или engine: нужны другое владение состоянием и координация. Локальное окно этого не обеспечивает.
- Требуется сохранять Python settings между рестартами: это отдельная задача хранения.
- Изменился способ определения effective roster: обновить правило samples и тесты после pruning.
